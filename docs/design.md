# 设计说明

这份文档记录的是**取舍**，不是功能清单。功能看 README 就行。

---

## 一、为什么版本只增不改

最直觉的做法是在 `Prompt` 上放一个 `template` 字段，改 prompt 就是更新这个字段。
大多数项目的做法。它省事，但代价是：**你永远失去了「上一次是怎么写的」。**

一旦丢失，三件事同时变得不可能：

| 能力 | 依赖什么 |
| --- | --- |
| 回滚 | 得知道旧内容是什么 |
| 对比 | 得同时存在两个版本 |
| 追责 / 复盘 | 得知道谁在什么时候为什么改的 |

所以我们把内容放进独立的 `PromptVersion`，`Prompt` 只保留一个指针 `currentVersionNo`。

```
Prompt (name, currentVersionNo=2)
  ├── PromptVersion v1  (不可变)
  └── PromptVersion v2  (不可变) ← 指针在这
```

**发布新版本**是修改内容的唯一入口。旧版本一个字都不会被动。

这个设计有个直接好处：**回滚变成一个赋值操作**，不需要复制内容、不需要删数据。
也因此，「回滚之后发现还是老的好，再回滚回去」是天然支持的 —— 这在 `template` 单字段方案里做不到。

### 为什么 `note` 是必填的

因为我们试过不填。

不填的结果是：三个月后你打开版本历史，看到 v3 和 v4 的 diff 只差一个词，但你完全想不起来当时为什么改。
**没有「为什么」的 diff，只是噪音。**

所以 `note` 在数据库层就是 `NOT NULL`。这不是洁癖，是防止未来自己骂现在自己。

## 二、断言为什么只用本地可判定的四类

这是整个项目最关键的一个取舍。

给 LLM 的输出打分，最"正确"的做法是再用一个模型来评分（LLM-as-a-judge）。
我们没这么做，只实现了四种纯本地的断言：

| 断言 | 判断依据 | 耗时 |
| --- | --- | --- |
| `CONTAINS` | 输出是否包含某段文字 | 微秒级 |
| `NOT_CONTAINS` | 输出是否**不**包含某段文字 | 微秒级 |
| `REGEX` | 输出是否匹配正则 | 微秒级 |
| `MAX_LENGTH` | 输出长度是否超限 | 微秒级 |

理由是一条硬约束：**回归测试必须能被无脑地、频繁地、免费地执行。**

如果每跑一次测试集要再花一次模型调用的钱，会发生什么？

1. 开发者只在"重要改动"后才跑 —— 而恰恰是小改动最容易出问题
2. 评分本身有随机性 —— 同一份输出两次评分可能不同，于是你分不清「分数降了」是 prompt 变差了还是评分抖动了
3. 跑一次要等几十秒 —— CI 里没人愿意加这一步

**所以本地断言不是"简化版"，而是"唯一能被信任的版本"。**

那复杂语义怎么测？两个办法，都留给了后续：

- **拆解成可判定的部分。** 「回答要有礼貌」不可测，但「不能出现『亲』」可测。把模糊要求翻译成具体约束，本身就是写好 prompt 的一部分 —— 顺带倒逼你把 prompt 写清楚。
- **引入独立的评分流程。** 让模型评分作为**可选**的第二层，只在需要时跑，且结果单独存，不和本地断言混在一起。

## 三、为什么没有 key 也要能跑

`mock-when-no-key` 这个开关，看起来是个方便功能，其实是个设计立场：

> **验证流程和验证效果是两件事，前者不该被后者卡住。**

一个新人 clone 下来，如果第一件事是「先申请一个 API key」，那他大概率就不会继续了。
有了 Mock 模式，他可以：

1. 完整走一遍：注册 prompt → 加用例 → 跑评估 → 看对比 → 回滚
2. 确认流程符合他的预期
3. 再去配 key，看真实效果

副作用也要说清楚：**Mock 模式下的分数不代表任何东西**。启动日志里会明确警告这一点 ——
把「流程跑通了」误读成「prompt 没问题」，比没有这个功能更糟。

## 四、为什么逐用例对比比通过率更重要

假设两个版本的通过率都是 75%，它们一样好吗？

不一定。可能是：

| 情况 | 版本 A 通过的用例 | 版本 B 通过的用例 | 结论 |
| --- | --- | --- | --- |
| 情况一 | 1、2、3 | 1、2、3 | 确实是同一个东西 |
| 情况二 | 1、2、3 | 1、2、4 | 修好一个、弄坏一个，**净变化是零，但绝对不是没变** |

单看通过率，这两种情况完全一样。而它们的含义天差地别。

所以对比接口返回的是**逐用例的判定**，其中 `REGRESSED`（之前通过、现在不通过）是唯一值得你立刻去看的一类：

```
REGRESSED   ← 这次改动弄坏了它。真正要看的
FIXED       ← 这次改动修好了它
STILL_PASS  ← 没受影响
STILL_FAIL  ← 一直没过（可能是用例本身有问题）
```

**「改动让分数降了 8%」是信息量很低的结论。「改动让『不承诺时限』这条坏了」才是可以行动的结论。**

## 五、已知限制

写下来是因为，一个项目对自身边界的描述，比它的功能列表更能说明它是否想清楚了。

| 限制 | 说明 |
| --- | --- |
| 没有并发控制 | 同一版本同时跑两次评估会产生两条记录，不会冲突，但也不会去重 |
| 评估是同步的 | 用例多 + 真实模型时，请求会阻塞较久。生产用需要改成异步任务 |
| 没有鉴权 | 内部工具定位，直接暴露接口。对外部署需要自己加 |
| 没有前端 | 当前只提供 REST 接口。加一个界面是明确的下一步 |
| 断言能力有限 | 见第二节，这是刻意取舍，不是遗漏 |
| 结果用 JSON 存 | 逐用例明细存在 `EvalRun.resultsJson`。要按用例做聚合分析时需要改成独立表 |

## 六、后续规划

按价值排序：

- [ ] 简单的 Web 界面：版本时间线、diff 视图、对比结果高亮 `REGRESSED`
- [ ] 变更门禁：通过率低于基线时拒绝「发布」这个动作
- [ ] 异步评估 + 进度查询（用例多时需要）
- [ ] 可选的模型评分层（与本地断言分开存储）
- [ ] 从代码里同步 Prompt：`@PromptSource` 注解，让 prompt 跟随 Git 走
- [ ] 聚类失败用例：把语义相近的失败归为一组，避免一次改 20 条用例

## 七、这个项目想证明的事

一句话：

> **AI 应用的可靠性问题，大部分不是「模型不行」，而是「工程没做」。**

Prompt 的版本管理、回归测试、回滚能力，在传统软件工程里是常识 —— 代码有 Git、有 CI、有回滚方案。
但换成 Prompt，这些常识全部消失了，大家的做法退化成了「在代码里改字符串，然后祈祷」。

这个项目想说的是：**这些常识是可以搬过来的，而且不难搬。**
